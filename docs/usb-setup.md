# Однократная настройка Omodash по USB

Нужны установленный подписанный `omodash.apk` **0.0.9 или новее**, Python 3.9+
и ADB из Android SDK Platform-Tools. На Mac с Android Studio скрипт сам находит
ADB в стандартном SDK. На Windows ищет PATH, ANDROID_HOME и LocalAppData/Android/Sdk.
Если SDK нет, [скачать Platform-Tools у Google](https://developer.android.com/tools/releases/platform-tools)
и указать путь к `adb` / `adb.exe` через `--adb`.

1. Припаркованная машина: включить USB ADB своей флешкой с ключом.
2. Подключить ноутбук USB-кабелем с передачей данных. На магнитоле подтвердить
   запрос отладки от ноутбука, если он появится. Это отдельная авторизация,
   не замена флешке. Держать ADB включённым до завершения настройки.
3. На Mac открыть `tools/setup-usb.command`, на Windows — `tools/setup-usb.cmd`.
   Либо из папки проекта выполнить:

   ```sh
   python3 tools/vehicle_usb.py setup
   ```

4. Дождаться `OK` у всех проверок прав и результата попытки включить TCP ADB
   на порту 5555. Если есть `НЕТ` или `ОШИБКА`, скрипт возвращает код 1 и объясняет
   проблему. Результаты выдачи прав и включения TCP ADB выводятся отдельно.
5. В лаунчере открыть Settings → Updates → Check updates. Автоподтверждение
   регулируется переключателем Automatically confirm this launcher's updates.
6. Права должны сохраняться при обычном обновлении APK с тем же сертификатом.
   После первой перезагрузки полезно проверить `status`, пока ноутбук рядом.

При нескольких подключённых устройствах скрипт остановится. Выбрать именно
магнитолу можно через `--serial НОМЕР_ИЗ_ADB_DEVICES`. Без USB-устройства,
при unauthorized/offline или при попытке подключения по IP он не выдаёт права.
`--allow-emulator` предназначен только для разработки; в автомобиле не нужен.

## Что меняет setup

Права выдаются только для `win.solobot.omodash` и активного пользователя Android:

- WRITE_SECURE_SETTINGS и READ_LOGS — служебная настройка и диагностика.
- ACCESS_FINE_LOCATION / ACCESS_COARSE_LOCATION — GPS, компас и погода.
- Реальное одобрение MediaListenerService через NotificationManager.
- Включение UpdateAccessibilityService с сохранением остальных сервисов.
- REQUEST_INSTALL_PACKAGES через AppOps — установка собственных обновлений.

В конце `setup` также пробует включить TCP ADB на порту 5555 для локального
помощника Android Auto. Это общая настройка `adbd` на ГУ. Скрипт выводит ответ
`adb tcpip`, ждёт возврата того же USB-устройства до 15 секунд и читает
`service.adb.tcp.port` и `init.svc.adbd`. `OK` означает, что команда выполнена,
порт настроен и `adbd` запущен; доступность сокета и авторизация ключа Omodash
проверяются при открытии Android Auto в приложении. Попытка выполняется и при
ошибке выдачи отдельных прав, но общий код завершения остаётся 1.

Скрипт открывает наш MainActivity и через защищённый приёмник восстанавливает
собственные компоненты, в том числе оставшиеся отключёнными после остановки
в старой версии или через USB-команду stop. Android 11 может отложить регистрацию служб; настройка
ждёт её завершения и проверяет живую привязку. При ручном запуске после выхода
хелпер может восстанавливаться около 15 секунд. Изменение установки APK на Android 11 может завершить
наш процесс; в конце скрипт открывает лаунчер снова. Он проверяет разрешения
PackageManager, AppOps, одобрение и живое подключение медиаслужбы, включение
и привязку хелпера, а затем дополнительно опрашивает Android API самого приложения
через защищённый DUMP-разрешением приёмник (включая canRequestPackageInstalls). Запись в Settings.Secure сама по себе не считается
подтверждением доступа к медиа. Повторный запуск допустим.

Нет root, смены Device Owner, установки/удаления APK,
очистки данных, смены default Home или изменений прав штатных приложений.
Не выдаются микрофон, body sensors, доступ ко всем файлам и прочие права,
не нужные для этих функций. Настройка не включает GPS глобально, если он выключен
в системе. Права позволяют пользоваться Android-медиасессиями; управление
проприетарным радио и встраивание Android Auto / CarPlay описаны отдельно в [инструкции проекции](projection.md).

## Проверка и диагностика зависаний

```sh
python3 tools/vehicle_usb.py status
python3 tools/vehicle_usb.py collect
python3 tools/vehicle_usb.py stop
python3 tools/vehicle_usb.py collect
```

`status` только читает состояние. `collect` сохраняет ZIP в `tools/usb-results/`:
до 6000 последних строк системного logcat, память нашего процесса, CPU системы,
процессы, состояние нашего пакета и параметры прошивки. Файлы ограничены размером;
системные логи могут содержать данные других приложений. Секретные ключи подписи
и ADB не собираются. В ZIP видно, если отдельный источник недоступен.
Команда **не открывает лаунчер**, поэтому пригодна и после его остановки.

`stop` требует приложение **0.0.9+**: через защищённый приёмник сначала
сохраняет и временно отключает собственные фоновые компоненты, затем выполняет
настоящий `am force-stop` **только нашего пакета** и проверяет
отсутствие его процессов и stopped-состояние. Затем не нажимать Home и не открывать
Omodash до проверки радио: default Home может снова запустить его. Если система
сразу поднимает наш Home, выбрать штатный лаунчер через настройки и повторить.
Скрипт сам назначение Home не меняет. При ручном запуске приложение снова заработает;
восстановление хелпера может занять около 15 секунд.

Если ALERT и обрывы сохраняются при подтверждённом отсутствии процессов Omodash,
это не объясняется текущей нагрузкой его живого процесса. Сохранить второй ZIP,
затем перезагрузить ГУ. Причину и возможное ранее вызванное изменение системного
состояния определять по журналам; одной кнопки выхода для такого вывода недостаточно.

Сбор ZIP через USB, force-stop и восстановление также проверены на отдельном
AOSP Android 11/API 30. Запреты прошивки не обходятся.

На этой машине установщик через pm, даже внутри sh -s, получил Restriction prevents
installing: в PackageManagerShellCommand прошивки есть отдельная Desay-проверка
mDSVForbiddenInstall. Пользователь установил APK вручную, после чего USB-скрипт
прав отработал успешно. Поэтому первая установка и выдача прав — разные этапы;
для установки сейчас использовать уже работающий путь через JCarTools/системный
установщик. Повторять pm install в надежде выдать права не нужно.

Особенность регистрации Accessibility в Android 11 проверена по [исходникам AOSP](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android-11.0.0_r48/services/accessibility/java/com/android/server/accessibility/AccessibilityManagerService.java):
после восстановления компонентов требуется обновить список служб и снять состояние
сбоя/force-stop у нашего хелпера. Остальные включённые Accessibility-сервисы не отключаются.


## Отложенная идея

Позже сделать сайт-установщик с USB-доступом из браузера: загрузка подписанного
APK, установка через ADB, запуск init-настройки прав и проверка результата.
Использовать тот же повторяемый сценарий настройки, не удалять данные при
восстановлении прав. Сайт — отдельная будущая задача, в текущую реализацию не входит.

## Android Auto в области плиток (0.0.14+)

Обычный `setup` уже пробует включить TCP ADB. Чтобы повторить только этот шаг,
выполните по USB:

```sh
python3 tools/vehicle_usb.py enable-android-auto
```

Команда включает TCP ADB на порту 5555. Omodash обращается только к локальному
`127.0.0.1`; в зависимости от adbd порт может быть доступен также по сети ГУ.
Откройте Android Auto в лаунчере и разрешите его ключ в запросе USB-отладки.
После полного перезапуска ГУ команда может потребоваться повторно.
Скрипт не устанавливает постоянные свойства adbd.

## Запуск с Android-телефона

Тот же Python-скрипт можно запускать из Termux, если телефон поддерживает USB Host
(OTG). Нужны Termux и Termux:API из одного источника, Python и
[termux-adb с поддержкой USB без root](https://github.com/nohajc/termux-adb).
Установите `termux-adb` по README его автора. Обычный ADB из `android-tools`
на телефоне без root не получает прямого доступа к USB-устройствам.

Включите USB ADB на ГУ своей флешкой, подключите телефон в роли USB Host
кабелем/OTG-переходником с передачей данных. Разрешите доступ к USB на телефоне
и подтвердите новый ключ отладки на ГУ. Распакуйте набор USB-tools на телефоне
и из его корня выполните в Termux:

```sh
pkg install python
termux-adb devices -l
python3 tools/vehicle_usb.py setup --adb "$(command -v termux-adb)"
```

`--adb` явно выбирает USB-совместимый `termux-adb`. Ноутбук при таком подключении
не нужен. Скрипт использует стандартную библиотеку Python; запуск через Termux
на конкретном телефоне и нашем ГУ пока не проверен.

Для восстановления только медиа можно использовать Bugjaeger на телефоне по USB
и выполнить в его удалённой shell, **без префикса `adb shell`**:

```sh
user_id=$(am get-current-user)
cmd notification allow_listener win.solobot.omodash/win.solobot.omodash.service.MediaListenerService "$user_id"
am start --user "$user_id" -n win.solobot.omodash/win.solobot.omodash.MainActivity
```

Это повторно одобряет доступ Omodash к уведомлениям/медиасессиям, но не заменяет
полную проверку `setup`. Удаление приложения также удаляет его сохранённые настройки.
Для включения TCP ADB в Bugjaeger используйте встроенную команду
**Commands → Connect through WiFi** —
[по документации автора](https://sisik.eu/blog/android/bugjaeger/connect-wifi)
она выполняет эквивалент `adb tcpip 5555`. Последующее подключение самого Omodash
идёт к локальному адресу ГУ и не требует общей Wi-Fi-сети с телефоном.
